Optimizer Step Processing Dynamics in Apple MLX: A Comparative Analysis of AdamW, Muon, and GEMM-Based OptimizersThe pretraining and fine-tuning of large language models (LLMs) fundamentally revolve around the intricate trade-off between optimization sample efficiency and the computational overhead incurred per step. Historically, deep learning paradigms relied almost exclusively on first-order, element-wise optimizers, with Adam and its weight-decay variant, AdamW, serving as the undisputed industry standards. However, the rapidly expanding parameter counts of modern architectures have catalyzed the advent of matrix-aware, higher-order optimizers. Frameworks such as Muon (MomentUm Orthogonalized by Newton-Schulz) and GEMM-based preconditioned optimizers like SOAP (ShampoO with Adam in the Preconditioner's eigenbasis) have demonstrably fractured the AdamW consensus. These modern optimizers achieve target validation losses in significantly fewer training steps by exploiting the spectral geometry and Kronecker-factored structural correlations of neural network weight matrices.While these geometric advantages drastically reduce the total token count required for convergence, they simultaneously impose a severe computational penalty, effectively transforming the optimizer step from a memory-bandwidth-bound operation into a heavily compute-bound operation. This paradigm shift creates unique challenges and opportunities within the Apple Silicon ecosystem, specifically when utilizing the MLX framework. Apple's Unified Memory Architecture (UMA) physically co-locates the CPU and GPU memory spaces, drastically altering the latency, bandwidth, and execution dynamics of the forward, backward, and optimizer update passes.In specialized repositories and configurations dedicated to local, low-memory LLM training—such as the conceptual and practical implementations surrounding [https://github.com/dtelcore/Apple-MLX-llm-gpu-8/—the](https://github.com/dtelcore/Apple-MLX-llm-gpu-8/—the) choice of optimizer dictates the delicate balance between achievable batch size, peak memory consumption, and wall-clock training time. Understanding the step processing times of AdamW (and its custom GPU-accelerated variants like AdamWGPU), Muon, and GEMM-based optimizers in MLX requires a rigorous architectural analysis of lazy evaluation computation graphs, Metal kernel dispatches, 8-bit quantization protocols, and advanced algebraic reductions such as the Gram Newton-Schulz algorithm.The Apple MLX Computational ArchitectureTo properly contextualize the performance profiles of various optimizers, it is imperative to deconstruct the execution mechanics of the Apple MLX framework. Unlike traditional deep learning frameworks such as PyTorch, which typically dispatch CUDA kernels eagerly to a discrete GPU, MLX is built fundamentally upon lazy (deferred) evaluation. When a typical optimizer update loop runs within MLX, the mathematical operations construct a directed acyclic computation graph in system memory but do not execute immediately on the hardware.Lazy Evaluation and Graph CompilationComputation is only materialized when an explicit evaluation trigger is invoked, such as calling mx.eval(), printing an array to the console, or converting an MLX array to a Python scalar or NumPy array. This deferred execution model is the cornerstone of step time optimization on Apple Silicon. It empowers the MLX compiler to perform extensive graph-level optimizations before any silicon is engaged. The compiler can seamlessly fuse element-wise operations, schedule work optimally across the CPU performance cores and the GPU, and eliminate redundant computations by tracking array dependencies.For a standard LLM training loop, the optimizer step calculates the updated parameters based on the gradients gathered during the backward pass. However, the computation graph remains entirely symbolic until a command like mx.eval(model.parameters(), optimizer.state) is explicitly executed. By wrapping these symbolic graphs in the mx.compile() transform, MLX can Just-In-Time (JIT) compile the optimizer step into highly optimized Metal shaders. The compilation process drastically reduces the Python interpreter overhead, caching the graph structure by input shape to ensure that subsequent optimizer steps execute with minimal CPU latency. This is particularly critical for higher-order optimizers that execute hundreds of intermediate matrix operations per step.Unified Memory Dynamics and Mixed ExecutionThe unified memory architecture of Apple Silicon fundamentally alters the memory traffic dynamics of the optimizer step, differentiating it sharply from discrete NVIDIA or AMD GPU configurations. In traditional setups, explicit host-to-device transfers (e.g., tensor.to('cuda')) create severe PCIe bandwidth bottlenecks. In contrast, MLX arrays reside in a shared physical memory pool accessible directly by both the CPU and the Metal-driven GPU. Consequently, there is no serialization or device transfer cost incurred when shifting computations.This architecture allows MLX to perform mixed-device execution asynchronously and with zero-copy overhead. Because there is no transfer cost, one can mix devices within a single computation block to maximize hardware utilization. The framework releases the Python Global Interpreter Lock (GIL) during mx.eval() or mx.async_eval(), permitting background CPU threads to continue processing dataloaders or handling web requests while the GPU executes the heavy optimizer computations in the background. For memory-bound optimizers like standard AdamW, the unified memory bandwidth sets the absolute ceiling on step time. For compute-bound optimizers like Muon, the parallel execution efficiency of the Metal General Matrix Multiplication (GEMM) kernels dictates the throughput.Custom Metal Kernels and Math ModesTo further accelerate custom optimizer logic, MLX allows researchers to bypass standard high-level array operations by writing custom Metal kernels via the mlx.core.fast.metal_kernel API. These JIT-compiled kernels allow for precise threadgroup dispatching and shared memory utilization. When deploying optimizers in low-memory, 8-bit configurations typical of projects like Apple-MLX-llm-gpu-8, these custom kernels are utilized to fuse quantization, step updates, and dequantization into a single execution pass. Furthermore, MLX provides compiler flags such as compile_options={"math_mode": "fast"} or "relaxed", allowing the Metal compiler to ignore strict IEEE compliance for special values (like NaN or -inf), thereby yielding higher ALU throughput during the dense floating-point operations characteristic of optimizer steps.First-Order Optimization: AdamW and AdamWGPUAdamW serves as the baseline against which all modern LLM optimizers are measured. As a first-order, element-wise adaptive optimizer, it calculates parameter updates by maintaining two exponentially decaying moments for each weight: the first moment (momentum) and the second moment (variance).The Memory-Bound Nature of AdamWThe update rule for AdamW is highly localized, applying scalar operations across flattened tensors. In the MLX environment, the step processing time for AdamW is almost entirely dictated by memory bandwidth rather than compute capability. For a parameter matrix of size $m \times n$, the AdamW step operates with an $O(mn)$ time complexity. Because it performs very few floating-point operations (FLOPs) per byte of data loaded from RAM, the arithmetic intensity is exceptionally low. The GPU's arithmetic logic units (ALUs) spend the vast majority of the step time idle, waiting for the massive first and second moment buffers to be fetched from unified memory and written back after the update.This memory-bound nature is severely exacerbated when scaling to multi-billion-parameter models. In standard 32-bit floating-point precision, AdamW requires 8 bytes of optimizer state per parameter (4 bytes for the momentum buffer, 4 bytes for the variance buffer). For a 7-billion parameter model, the optimizer state alone consumes roughly 56 GB of memory, which easily exceeds the unified memory capacity of standard Apple Silicon machines unless advanced offloading or quantization techniques are employed.AdamWGPU and 8-bit Quantized StatesConfigurations targeting local GPU constraints, such as the 8-bit regimes explored in frameworks resembling Apple-MLX-llm-gpu-8, actively seek to compress this optimizer state. Recent state-compression innovations, such as Gefen-X and FlashOptim, have demonstrated that the AdamW state can be quantized down to approximately 1 byte per parameter (or 7 bytes total including gradients). By mapping the variance and momentum tensors into heavily compressed lookup structures using companding functions, these implementations cut the optimizer memory footprint by up to a factor of eight while maintaining standard AdamW-level convergence trajectories.In MLX, an "AdamWGPU" implementation utilizes highly optimized custom Metal kernels to execute these compressed updates efficiently. Using mlx.core.fast.metal_kernel, the optimizer can perform state decompression, the element-wise AdamW scaling calculation, and re-compression entirely within the GPU's registers. This prevents the intermediate 32-bit upcasting that characterizes naive 8-bit optimizer implementations, which would otherwise cause massive transient spikes in peak memory consumption. By maintaining only a single momentum buffer, Lion matches the 4-byte-per-parameter memory footprint of Muon, while retaining the $O(mn)$ linear time complexity of AdamW. Signum (Sign Momentum) operates on a similar principle, relying purely on the sign of the gradients to determine the descent direction, prioritizing speed and memory efficiency over the nuanced scaling provided by second-moment estimation.The Orthogonalized Paradigm: Muon and Spectral Norm GeometryWhile AdamW scales easily from an engineering perspective, its element-wise nature inherently ignores the correlational structure between gradients and the geometric operator nature of neural network weight matrices. LLM weights are not merely collections of independent scalars; they are linear transformations mapping latent spaces. This theoretical limitation has driven the rapid adoption of Muon (MomentUm Orthogonalized by Newton-Schulz), which has proven instrumental in training frontier sparse and dense models, including Kimi K2, GLM-5, and DeepSeek-V4.Muon operates on a fundamentally different geometric premise: it is explicitly designed to optimize two-dimensional weight matrices by performing steepest descent under the spectral norm. Instead of scaling individual scalar elements by their historical variance, Muon treats the entire gradient matrix as a unified geometric operator. At each training step, Muon calculates the gradient, computes an exponentially moving average to form the momentum, and then applies a polar decomposition to orthogonalize the momentum matrix before applying the update to the weights.The Mathematics of Muon and SVD ApproximationMathematically, for a momentum matrix $M_k \in \mathbb{R}^{n \times m}$ at step $k$, the ideal orthogonalized update is the polar component derived from the Singular Value Decomposition (SVD). If the SVD of the momentum is $M_k = U \Sigma V^\top$, the polar decomposition is:$$\text{polar}(M_k) = M_k (M_k^\top M_k)^{-1/2} = U V^\top$$
By extracting only the orthogonal matrices $U$ and $V^\top$, Muon effectively replaces the singular values of its momentum matrix with exactly one, producing an update with a perfectly flat singular spectrum. This perfectly spatial decorrelation allows the neural network to navigate the loss landscape without the poor conditioning that typically plagues deep linear transformations.Because computing exact SVDs during every optimizer step is computationally disastrous for large neural networks, Muon approximates the polar decomposition using the Newton-Schulz iteration. The algorithm takes the Frobenius-normalized momentum matrix and repeatedly applies an odd-degree matrix polynomial to push its singular values toward 1. A standard Newton-Schulz iteration updates a matrix $X_t$ as follows:

$$
X_{t+1} = \frac{1}{2} X_t (3I - X_t^\top X_t)
$$

In modern implementations, higher-degree polynomials (e.g., degree-5) are utilized to achieve convergence in fewer iterations.The Computational Overhead on MLXThe theoretical superiority of Muon translates into profound sample efficiency. Empirically, on language modeling tasks and NanoGPT speedrunning benchmarks, Muon reaches target validation losses up to 25% to 35% faster in terms of training tokens compared to AdamW. However, this token efficiency comes at a severe cost to the step processing time.The Newton-Schulz iterations in Muon require dense matrix multiplications, fundamentally shifting the optimizer step from a memory-bound operation to an ALU-bound (compute-bound) operation. For a weight matrix of dimensions $m \times n$, performing the Newton-Schulz iteration costs $O(mn^2)$ time assuming $n \le m$. In a typical MLX setup requiring five iterations of degree-5 polynomials, the optimizer must execute multiple rectangular matrix multiplications per layer, per step.On Apple Silicon, these GEMMs are routed through the Metal backend via mlx.core.fast.metal_kernel or standard mx.matmul dispatches. While MLX handles GEMMs efficiently, the sheer volume of floating-point operations introduces a massive latency spike at the end of the backward pass. Furthermore, Muon's memory characteristics present a dichotomy. On one hand, it requires only a single momentum buffer per parameter, halving the optimizer state memory compared to full-precision AdamW (4 bytes vs 8 bytes). On the other hand, the Newton-Schulz iteration requires transient activation memory to hold the intermediate matrix states of the polynomial terms, such as $X_t^\top X_t$ and $(X_t^\top X_t)^2$. In unified memory systems, this transient spike can trigger severe memory pressure, forcing the system to evict caches or page data, which subsequently elongates the step processing time and nullifies the benefits of the smaller resting optimizer state.Hardware-Aware Algebraic Reductions: Gram Newton-Schulz and Dion3To mitigate the cubic scaling overhead of standard Muon on hardware accelerators, algorithmic revisions such as the Gram Newton-Schulz (GNS) algorithm and the Dion3 framework have been developed. These revisions dramatically alter the step time dynamics, transforming Muon from an impractically slow theoretical curiosity into a production-ready optimizer.Overcoming Rectangular InefficienciesThe standard Newton-Schulz algorithm performs poorly on modern transformer architectures because the weight matrices are often highly rectangular. For instance, in fine-grained Mixture-of-Experts (MoE) layers or expanded Feed-Forward Networks (FFNs), dimensions often take the shape of $m \times n$ where $m \gg n$ (e.g., an aspect ratio of 8). The runtime of standard Newton-Schulz is heavily dependent on the larger dimension, requiring up to 10 rectangular matrix multiplications for a standard five-step approximation.The Gram Newton-Schulz approach exploits algebraic equivalences to bypass these large rectangular GEMMs entirely. GNS recognizes that the polar decomposition can be computed by isolating the Gram matrix of the momentum. Instead of iterating directly on the massive rectangular matrix $X \in \mathbb{R}^{n \times m}$, GNS first computes the small, square, symmetric Gram matrix $R_0 = XX^\top \in \mathbb{R}^{n \times n}$. It then executes the Newton-Schulz-style polynomial iterations entirely within the much smaller $n \times n$ subspace to find a matrix $Q_t$ that converges to the inverse square root $(XX^\top)^{-1/2}$. Only at the final step is this square matrix multiplied back against the rectangular matrix to yield the orthogonalized update.FLOP Reduction and Symmetric GEMMs in MLXThis restructuring yields profound performance advantages for MLX implementations:Algorithmic FLOP Reduction: The theoretical floating-point operation (FLOP) count drops from approximately $T(3\alpha + 1)n^3$ in the standard method to just $(4T + 3\alpha - 3)n^3$ in GNS, where $\alpha = m/n$ is the aspect ratio of the matrix and $T$ is the number of iterations. For transformer projection matrices with an aspect ratio of 8, GNS reduces the raw computational workload by up to 50%.Symmetric GEMM Exploitation: Because the Gram matrix $XX^\top$ and its subsequent polynomial powers are perfectly symmetric by definition, specialized symmetric GEMM kernels can be deployed. Rather than calculating the full dense output matrix, a symmetric kernel computes only the lower triangular portion and seamlessly reflects the results to the upper triangular portion.When executed on Apple Silicon via MLX, Gram Newton-Schulz transforms the Muon step from a prohibitive bottleneck into a highly optimized subroutine. Although writing custom symmetric GEMM kernels in Metal requires precise threadgroup management to avoid divergent branching, the net result is a Muon step that executes in roughly half the wall-clock time of a naive Muon implementation.Stability and the Dion3 Megabatching ProtocolHowever, GNS is highly susceptible to numerical instability when utilizing low-precision arithmetic formats (like bfloat16), which are standard in MLX to maximize memory bandwidth. To address this, implementations employ "restarts"—a stabilization technique where the Gram matrix is periodically reconstructed from the intermediate rectangular state to flush out accumulated floating-point errors and eliminate spurious negative eigenvalues.Further optimizations are found in frameworks like Dion3, which introduces megabatching and fractional row updates to Muon. By defining a hyperparameter $f \in (0, 1]$ representing the fraction of rows to update, Dion3 targets only a subset of the matrix rows featuring the largest $\ell_1$ norms. This reduces the dimensionality of the Gram matrix even further, heavily compressing the communication overhead and compute requirements, which is vital when distributing MLX workloads across multiple Apple Silicon nodes via Thunderbolt RDMA (as seen in specific MLX cluster benchmarks).Kronecker Preconditioning: SOAP and Shampoo DynamicsBeyond spectral orthogonalization, GEMM-based optimizers utilizing Kronecker-factored preconditioning represent another frontier in LLM training efficiency. The Shampoo optimizer, and its modern derivative SOAP (ShampoO with Adam in the Preconditioner’s eigenbasis), aim to precondition the neural network gradients using second-order statistical information without explicitly forming the prohibitively massive inverse Hessian matrix.SOAP approximates the Fisher information matrix using the Kronecker product of two smaller, more manageable matrices. These matrices represent the statistics of the forward-pass activations and the backpropagated errors, respectively. By projecting the gradients into this eigenspace before applying Adam-style exponential moving average updates, SOAP achieves a highly effective descent direction that navigates the loss landscape optimally, avoiding the sharp, unstable local minima to which first-order methods like AdamW often fall victim.Amortized Eigendecomposition Step TimesThe step processing time for SOAP introduces entirely different latency constraints compared to Muon. While Muon applies the Newton-Schulz approximation iteratively at every single training step, SOAP requires the precise computation of inverse $p$-th roots of the preconditioner matrices (often executed via exact SVD or Schur decompositions). Because performing an exact eigendecomposition at every step is catastrophically slow, SOAP implementations amortize this computational cost by calculating the eigenbasis infrequently—typically updating the preconditioners only every 100 to 500 steps.In the MLX framework, this amortization creates a highly uneven step processing time profile. The vast majority of optimizer steps act similarly to a standard matrix projection, executing rapidly. However, the specific steps where the eigenbasis is refreshed encounter massive latency spikes.Large-Batch ScalingDespite the uneven step times, SOAP scales exceptionally well at extremely large global batch sizes. This makes SOAP highly attractive for massive-scale cluster pretraining. A transformer model, however, contains numerous critical 1-dimensional parameters, including Layer Normalizations (RMSNorm), bias vectors, and massive token embeddings.Furthermore, empirical experiments reveal that attempting to apply pure Muon across an entire network (by artificially reshaping 1D tensors) often results in severe spectral-norm inflation. This inflation manifests as catastrophic gradient norm spikes, which destabilize the training run and invariably lead to the exploding attention logit crisis.The Muon + AdamW Split ArchitectureTo circumvent these mathematical realities, state-of-the-art frameworks—including MLX-based trainers and frontier models like Qwen 3.8 Flash Next—uniformly deploy hybrid optimizer regimes. In this hybrid regime, Muon or SOAP is explicitly assigned to the 2D linear map parameters, while a highly tuned AdamW (or a quantized variant like Gefen-X) governs the 1D parameters.This hybridization fundamentally dictates the step processing execution flow in MLX. During an optimizer.update() call, the MLX lazy computation graph diverges into two entirely distinct subgraphs. The 1D parameters traverse an element-wise AdamW path, invoking fast, parallelized memory access patterns. Simultaneously, the 2D parameters traverse the compute-heavy Newton-Schulz path. Because MLX compiles these operations dynamically, the framework's Metal backend can theoretically interleave the memory-bound AdamW updates with the compute-bound Muon updates, maximizing the utilization of the M-series GPU.Stability Solutions: MuonClip and Soft MusecIn environments where even the hybrid approach exhibits instability, researchers deploy constraint mechanisms. "MuonClip," utilized famously in the Kimi K2 1T-parameter model, applies QK-norm clipping to the Muon updates to stabilize massive pretraining runs. However, in smaller-scale fine-tuning environments (such as a 4B parameter model fine-tune), MuonClip was shown to underperform the standard Muon+AdamW hybrid, resulting in lower token accuracy and slower convergence due to the overly aggressive clipping.Alternatively, Soft Musec offers an architecture-agnostic mechanism for stabilizing Muon training. In these strictly time-bound environments, the optimizer's per-step wall-clock execution speed is pitted directly against its per-step convergence efficiency.
